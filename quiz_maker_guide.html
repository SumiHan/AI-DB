① GitHub Pages — 웹 호스팅 (내 HTML을 인터넷 주소로)

GitHub는 파일을 올려두는 저장소(창고)이고, Pages는 그 창고의 HTML 파일을 누구나 접속 가능한 웹페이지로 바꿔주는 기능입니다. 서버를 사거나 설치할 필요 없이 https://...github.io/... 형태의 공개 주소가 무료로 생깁니다. 여러분이 만든 퀴즈 화면(프론트엔드)이 여기서 열립니다.

② 구글 스프레드시트 — 데이터베이스 역할

응답이 쌓이는 표입니다. DB 수업에서 배우는 용어로 그대로 바꿔 볼 수 있어요.

스프레드시트 용어데이터베이스 용어이 실습에서는
시트(탭)테이블(table)'요약' 테이블, '문항별' 테이블
한 줄(row)레코드(record)제출 1건 / 문항 1개
열(column)필드·속성(field)이름, 점수, 등급 …
맨 윗줄스키마(헤더)각 열이 무슨 값인지 정의
DB 포인트 · '요약'과 '문항별'을 이름(name)이라는 공통 값으로 이어 보면, 한 테이블만으로는 알기 어려운 것(누가 어떤 문항을 틀렸나)을 두 테이블을 조인(join)해서 알아내는 감을 잡을 수 있습니다.

③ Apps Script — 백엔드(서버) 역할

퀴즈 화면에서 보낸 데이터를 받아서 스프레드시트(DB)에 한 줄 추가(INSERT)해 주는 작은 프로그램입니다. 배포하면 생기는 웹 앱 URL이 곧 API 주소이고, 코드 안의 doGet()이 요청을 받아 appendRow()(= SQL의 INSERT)로 저장합니다.

한 문장 요약 · 학생이 퀴즈를 풂(GitHub Pages) → 결과가 URL로 전송됨 → Apps Script가 받아서 → 구글 시트(DB)에 저장. 이 흐름이 오늘 여러분이 직접 만들어 볼 웹 서비스의 축소판입니다.
1
DB 개념으로 5지선다 만들기

수업에서 배운 DB 개념(테이블·기본키·SQL·정규화·트랜잭션 등)을 문제로 바꿉니다. 좋은 객관식의 5가지 원칙:

  1. 질문은 하나만 — 한 문항에서 한 가지만 물어봅니다.
  2. 정답은 명확하게, 오답은 그럴듯하게 — 오답도 "헷갈릴 만큼" 만들어야 좋은 문제입니다. (예: 기본키 vs 외래키 vs 인덱스)
  3. 보기 길이·형식을 비슷하게 — 정답만 유난히 길면 티가 납니다.
  4. 정답 위치를 골고루 — 정답이 계속 2번에 몰리지 않게 A~E에 분산합니다.
  5. 해설을 꼭 답니다 — 왜 정답인지 한두 문장. 푸는 사람이 배웁니다.
문제로 만들기 좋은 소재 · 용어 정의("~를 무엇이라 하는가?"), 개념 구분("~와 ~의 차이"), SQL 결과 예측("이 SELECT 문의 결과는?"), 상황 판단("이럴 때 가장 적절한 것은?").

자주 묻는 질문

    
Q. 페이지는 열리는데 결과가 시트(DB)에 안 들어와요.

    
대부분 배포 설정 문제입니다. Apps Script 배포에서 액세스가 모든 사용자인지 확인하고, 코드를 고쳤다면 새 버전으로 다시 배포해야 반영됩니다.

    
Q. 화면이 하얗게만 나와요.

    
편집 구역에서 따옴표나 쉼표가 하나 빠졌을 가능성이 큽니다. 특히 마지막 문항 뒤 쉼표, 보기 사이 쉼표를 확인하세요.

    
Q. 스프레드시트가 데이터베이스라고요?

    
정식 DBMS(MySQL 등)는 아니지만, 테이블·레코드·필드라는 구조와 데이터를 추가·조회하는 원리는 똑같습니다. 그래서 DB를 처음 체험하기에 좋은 도구입니다.

    
Q. 문항을 나중에 더 추가하려면요?

    
파일에서 { ... } 덩어리를 복사해 늘린 뒤, GitHub에서 같은 파일을 다시 업로드(덮어쓰기)하면 됩니다.
